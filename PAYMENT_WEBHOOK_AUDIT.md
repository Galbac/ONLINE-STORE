# Аудит платёжных webhook — 6 октября 2026

Проверены исходники, локальная конфигурация, шаблон Nginx и unit-тесты. Настройки боевых личных кабинетов, секреты из БД и реальная доставка уведомлений не проверены. Деплой не выполнялся.

## Защита и исправления

- ЮKassa: подтверждение объекта авторизованным GET к API провайдера. Клиентский статус и сумма не используются как доказательство оплаты. Поддерживаются `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`, `refund.succeeded`; остальные события игнорируются.
- Robokassa: ResultURL GET/POST, обязательная подпись с Password #2, сравнение через `hmac.compare_digest`. MD5 сохранён для совместимости; SHA-256/SHA-512 доступны через `ROBOKASSA_HASH_ALGORITHM`, который должен совпадать с настройками магазина.
- Запрещены повторные поля формы/JSON, противоречащие ID, неверные типы metadata, слишком большие номера счёта. Размер входящего запроса ограничен во время чтения потока; `PAYMENT_WEBHOOK_MAX_BODY_BYTES=65536`.
- Проверяются провайдер, ID платежа, внешний ID, сумма и валюта. Robokassa `InvId` связан с ID записи платежа, `Shp_order_number` — с заказом. Новые внешние ID уникальны для каждой попытки платежа; ранее созданные ссылки с номером заказа поддерживаются.
- Ключ дедупликации стабилен и включает провайдера, событие и объект. Существуют PostgreSQL advisory lock и уникальный индекс журнала; платеж и заказ блокируются при обработке. Поздняя отмена/холдирование не перезаписывают оплату или возврат.
- Для Robokassa ответ `OK{InvId}` возвращается после обработки; для ЮKassa — HTTP 200. При отсутствии ещё не закоммиченного платежа или ошибке API/транзакции успех не подтверждается, чтобы провайдер мог повторить доставку.
- Подпись и сырое тело Robokassa больше не сохраняются в журнале.

## Что нужно настроить при запуске

URL обеих интеграций: `https://<реальный-домен>/api/payments/webhook`. Поле `PAYMENT_WEBHOOK_URL` не регистрирует endpoint автоматически в кабинетах провайдеров.

ЮKassa: указать URL в кабинете и включить перечисленные выше события; задать Shop ID и Secret Key в админке или окружении. `X-Payment-Signature` не является подписью стандартного webhook ЮKassa: рабочая проверка основана на запросе объекта через API. Старые параметры `PAYMENT_PROVIDER_WEBHOOK_SECRET` и `PAYMENT_WEBHOOK_VERIFY_SIGNATURE` не выключают эту проверку.

Robokassa: настроить основной ResultURL, HTTP GET или POST, одинаковый алгоритм подписи в кабинете и приложении. Password #1 используется при формировании оплаты, Password #2 — только для ResultURL; они должны различаться. Тестовые и боевые учётные данные должны быть разделены. JWS-уведомления ResultUrl2 этим обработчиком не поддерживаются. SuccessURL не является подтверждением оплаты.

В проверенном локальном `.env` указан шаблонный `https://api.site.ru/api/payments/webhook`, ключи обоих провайдеров не заданы. Настройки в БД имеют приоритет, поэтому эти значения сами по себе не доказывают неисправность боевой интеграции.

## Оставшиеся ограничения

1. После коммита оплаты очистка кешей и отправка уведомлений выполняются отдельно. Если процесс упадёт в этот момент, повтор webhook встретит уже обработанное событие и не восстановит все побочные действия. Для гарантированной доставки нужен транзакционный outbox с фоновым обработчиком; финансовый статус уже сохранён.
2. Ротация магазина/секретов для незавершённых платежей не поддерживается отдельно: проверка использует текущие настройки. Нельзя менять реквизиты, пока старые платежи/возвраты ожидают уведомлений, без процедуры перехода.
3. Robokassa здесь подтверждает оплату; её возвраты через webhook не реализованы. ЮKassa поддерживает частичные возвраты, но в данном аудите не выполнялись реальные возвраты или конкурентные испытания на PostgreSQL.
4. Защита от подделки ЮKassa не ограничивает число запросов к API провайдера со стороны атакующего. В шаблоне Nginx есть общий rate limit; в боевой инфраструктуре необходимо проверить его действие, HTTPS и доверенные прокси. IP allowlist можно использовать как дополнительный слой, но не принимать произвольный `X-Forwarded-For` за доказательство происхождения запроса.
5. Нет подтверждённого сквозного тестового платежа в кабинетах. Нельзя утверждать, что webhook «максимально безопасен» или полностью настроен на проде только по unit-тестам.

Документация: [ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [Robokassa](https://docs.robokassa.ru/ru/notifications-and-redirects).
